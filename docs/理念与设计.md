# slab：一颗直接运行的 shell 种子

slab 不是另一个更厚的 AI 编程助手。它问一个很窄的问题：**只用 POSIX `/bin/sh`，能不能撑住一个带工具的 coding-agent 主循环？**

仓库现在只有一个产品形态：根 [`seed.sh`](../seed.sh)。它同时是唯一源码和完整 standalone runtime，直接维护、直接运行；没有 build/pack 阶段，也不会生成另一份 agent 引擎。历史上的安装包与多形态讨论保存在 `docs/superpowers/specs/` 和 `docs/superpowers/plans/`，仅供追溯，不是当前规范。

---

## 1. 一颗文件如何工作

第一次在目标项目目录启动：

```sh
/bin/sh /path/to/seed.sh deepseek sk-xxxx
```

种子会把配置保存到状态目录（默认 `~/.seed`，可用 `SEED_HOME` 覆盖），拉取 agent catalog，探测本机能力并写入 Machine index，然后进入 `>`。之后在任意项目目录运行同一个文件即可：

```sh
/bin/sh /path/to/seed.sh
/bin/sh /path/to/seed.sh -p "完成一个独立任务"
```

工作区永远是**启动命令时的当前目录**。runtime 文件在哪、状态目录在哪、正在修改哪个项目，是三件互相独立的事。

交互里的 `/ini` 会让模型选择适合本机的用户级安装方法，把当前 runtime 暴露为全局命令 `seed`。模型负责执行，外壳负责公证。成功后可以在任意项目中：

```sh
seed
seed -p "任务"
```

不再生成 `bin/agent` 或一组工具 shim；`seed.sh` 本身始终是完整引擎。

## 2. 为什么主循环必须属于外壳

循环形状固定：

```text
messages + 两个 tools 请求模型
  → 有 tool_calls：依次执行，把 observation 作为 tool 消息喂回
  → 没有 tool_calls：结束本轮，只输出最终回答
```

模型决定看什么、改什么、什么时候结束。外壳决定请求、执行、错误、轮数和终端行为。不要让模型每一轮另写 controller，也不要用 Python/Node 实现 loop 后再套一层 shell。

runtime 的 loop、SSE、工具调用和状态处理只用：

- POSIX `/bin/sh`
- curl
- jq

模型为用户项目生成 Python、Go、JavaScript 或任何别的语言不受限制；那是任务产物，不是 runtime 作弊。

## 3. 两个 API 工具

模型只看到两个标准 `tool_calls` 工具：

| 工具 | 契约 |
|---|---|
| `shell` | 在同一个持久登录壳中运行命令，`cd` 和环境变量跨调用保留 |
| `edit` | 把文件中的 `old_text` 唯一替换为 `new_text`；匹配 0 次或多次都失败且不改文件 |

查看文件、搜索、列目录、运行测试和创建文件都通过 shell 中的普通命令完成。read、grep、glob、todo、子代理不作为新 API 工具加入。

“只有两个工具”不是“只能做两件事”。本机已有的 CLI、库、服务和网络资料经过探测、smoke 和登记后，都由 shell 使用。能力索引的原则是：**先找、验证、登记、复用，找不到才造。**

持久 shell 跟随宿主 `$SHELL`（缺失时用 `/bin/sh`）；worker 自身仍以 POSIX sh 启动。edit 用 jq 做字符串运算，不依赖 GNU/BSD 两套 `sed -i`。

## 4. 状态、凭据与证据

状态根只使用：

```text
~/.seed
SEED_HOME=/另一个隔离目录
```

其中包含保存的 `.env`、agent catalog、Machine index 和初始化状态。没有旧环境变量或旧目录 fallback。API key 不应写进项目，不进入消息证据，不得打印或提交。

任务证据默认在工作区 `.agent-runs/`：messages、模型 turn、工具参数与 observation、usage。一次交互窗口共享一段持久 shell 会话；每个任务有自己的事件目录。可以用 `AGENT_RUNS_DIR` 在测试或 benchmark 中隔离。

`--probe` 不调用模型、不联网、不输出 key，提供稳定身份：

```text
seed.identity=seed
seed.version=...
seed.state=...
seed.workspace=...
```

---

## 5. `/ini` 为什么仍然需要外壳验收

模型可以选择复制 runtime、创建软链接或写一个极小 POSIX shim，但不能自己宣布成功。外壳至少验证：

1. `install-result.json` 的命令名是 `seed`，entry 是安全绝对路径且可执行；
2. 用启动时冻结的原始 PATH 解析 `seed`，结果必须正好等于回执 entry；
3. 运行 entry 的 `--probe`，身份、版本、状态目录必须匹配。

运行期间为了 jq 临时加入 PATH 的私有目录不能冒充全局安装位置。未来登录也许生效的 profile 修改，不等于当前已验证可用。

---

## 6. catalog 与会长大的能力索引

`plugins/agent/` 保留 catalog 架构。catalog 发布 JSON prompt 与初始化树，不发布另一套 runtime、平台启动器或工具动物园。

首次启动时，引擎确定性探测基础命令；初始化 prompt 再建立环境和资源索引。skills、commands、models、plugins、delegate 等块按任务需要懒构建，一次性任务不应为了扩展而延期。

Machine index 中的资源必须记录用途、调用方式、依赖、smoke 结果和时间。可用条目标 `ok:true`；缺 key 或验证失败的条目保留为 `ok:false` 并写明原因。失效时更新状态，不凭空发明能力。

全局安装后的委派也是普通 shell 调用：`seed --oneshot '<self-contained task>'`。它不是第三个 API 工具。全局命令尚未安装时，应先由人运行 `/ini`，而不是偷偷恢复一套项目内入口。

---

## 7. 可移植边界

同一份 `seed.sh` 要能在 macOS、Linux、WSL、Git Bash 的 POSIX 环境运行。不要假设 Bash 5，也不要依赖 `timeout(1)`、`pgrep`、`head -c`、GNU `sed -i` 等平台特性。原生 cmd / PowerShell 不在当前边界内。

路径不得烘焙某台机器的 `/Users/...` 或 `/home/...`。runtime 可以知道自己的文件位置和状态根，但 shell 工具的 cwd 必须是启动时的项目目录。

---

## 8. 终端体验

第一次打开显示 `initializing:`，完成后显示 `ready` 并进入 `>`；之后直接进入提示符。初始化和对话保留既有 SSE/工具过程反馈，最终回答只打印一次。空行或 EOF 退出。

已有可见行为默认保留。修 bug 应补合同和实现，不应顺手删掉初始化、流式显示或证据。需要改变产品行为时先明确取得批准。

---

## 9. 仓库与验证

当前维护面：

```text
seed.sh                    唯一产品、runtime、源码
tests/seed-package.sh      离线合同
plugins/agent/             agent prompt catalog
plugins/seed/              provider/model catalog
plugins/jq/                jq fallback 镜像
bench/                     Apple container 与 Harbor benchmark
docs/理念与设计.md          当前设计说明
```

修改 `seed.sh` 后不需要打包，直接验证：

```sh
/bin/sh -n seed.sh
/bin/sh tests/seed-package.sh
git diff --check
```

合同测试必须离线，用假的 plugin transport 和 LLM stub 覆盖首次激活、状态隔离、工作区、持久 shell、精确 edit、oneshot、probe 和 `/ini` 验收，不依赖真实 key。

这就是 slab 当前的形状：**一个文件、一个循环、两个 API 工具、一张会长大的能力索引。**
